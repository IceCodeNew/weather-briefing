# 技术取舍

本文只解释乍看不够理想、但目前有意保留的选择。正常的模块拆分和通用实现不在这里重复。当前实现见[系统设计](design.md)。

每项都说明选择、成立条件和重新评估的时机。

## 完整天气服务仍返回多种能力

天气能力已经分开建模，但和风天气和 Open-Meteo 仍通过一次完整流程返回天气、空气质量、生活指数或过敏原。

为了类型上的纯粹而拆成多次请求，会增加延迟、配额消耗和部分失败状态。因此完整服务目前放在天气槽位，只有真正独立的服务才进入其他能力槽位。

这项选择成立的条件是厂商接口仍适合一次组合调用。如果某项能力可以独立调用，并且确实需要单独替换或路由，就增加对应的薄适配器。

`ALLERGEN` 只表示结构化过敏原数据，不表示任何过敏建议。和风天气的综合过敏指数属于生活指数，即使它会触发过敏建议。

如果厂商以后提供具体花粉种类和浓度，再把它声明为结构化过敏原能力。

## 默认简报语言是英文

简报语言以前是隐含行为。变成配置项后，产品级默认值选择英文，现有中国大陆示例则显式填写 `zh-CN`。

这样不会把一个地区的旧行为误设为全世界的默认值，也能让旧部署通过明确配置保留原有输出。

如果产品以后有可靠的用户语言来源，可以重新评估是否在首次配置时提供建议值。程序不能只根据坐标猜测用户想读的语言。

## 简报语言不写入定位缓存

地点语言是用户当前选择，不是定位服务返回的事实。因此缓存只保存坐标、行政区和时区；每次运行都从地点配置覆盖简报语言。

代价是所有缓存命中路径都必须执行覆盖。如果语言开始影响定位服务返回的名称或行政区，就把语言加入缓存键，而不是继续复用当前缓存。

## 只支持基础 BCP 47 标签

当前内置服务和地点配置只需要语言、脚本和地区部分。完整支持 Unicode 扩展和私有子标签需要引入成熟解析库，当前没有实际收益。

因此实现只接受基础标签，并按主语言逐步匹配服务支持的输出语言。

如果外部服务、持久化格式或用户配置开始需要扩展子标签，就改用成熟的 BCP 47 解析器，并重新检查规范化和匹配规则。

## 保留旧 DeepSeek 环境变量

项目在引入 any-llm 之前直接读取 `DEEPSEEK_MODEL` 和 `DEEPSEEK_BASE_URL`。改用 any-llm 后，通用模型名称改由 `LLM_MODEL` 提供，DeepSeek 的 API Base 则使用 SDK 约定的 `DEEPSEEK_API_BASE`。

为了不让已有部署在升级时立即失效，配置入口仍接受旧变量。只有对应的新变量没有填写时，旧变量才作为后备；新旧变量同时存在时始终采用新变量。

这是针对历史 DeepSeek 部署的定向兼容，不是为所有模型厂商维护第二套配置名称，也不能扩展成通用的 provider 配置注册表。

如果以后发布明确允许删除旧配置的重大版本，并且迁移说明已经给已有部署留出足够时间，就可以移除这两个后备变量。在此之前，修改模型配置边界时必须保留并测试这一优先级。

## LLM 自定义 header 复用 provider client 参数

[mozilla-ai/any-llm#707](https://github.com/mozilla-ai/any-llm/pull/707) 为 any-llm 的无状态 completion API 增加了 `client_args`，并把其中的 provider-specific 参数展开传给 `AnyLLM.create()`。应用需要跨多次请求持有并显式关闭 provider client，因此不调用每次重新创建 client 的无状态 API，而是直接复用它的底层通道：把解析后的 header 映射放入本地 `client_args["default_headers"]`，再以 `AnyLLM.create(provider, **client_args)` 创建受应用管理的 provider。代码没有调用 #707 新增的具名参数，但使用的是同一条 provider client 参数透传路径。

升级 any-llm 或 provider SDK、新增 provider，或者 any-llm 提供统一且带能力声明的 header 接口时，必须重新检查 provider client 构造函数和实际请求，更新黑名单或改用统一接口。

## FallbackLLMProvider 在进程内保持粘性

这是一个有意保留的自定义外部服务集成。选择 `FallbackLLMProvider` 的原因是 any-llm 只统一调用单个 provider，不编排跨 provider 的故障切换。包装器捕获主适配器的 `LLMRequestError`，切换后在剩余生命周期内固定使用备用适配器，使同一进程里的契约修复不会回到刚刚失败的主服务。

适配器把应用工厂创建的 AnyLLM provider client 在 completion 调用中抛出的异常归一化为 `LLMRequestError`，使配置正确的 fallback 能够启动。请求消息在进入该边界前完成序列化，因此应用自身的序列化错误不会触发 fallback；结构化输出的 Pydantic 校验错误和直接注入协议实现所抛出的异常继续原样传播。

它替代的是每个调用点手写的故障切换分支，不替代 any-llm 的厂商适配器，也不接管 SDK 凭据、请求重试或输出验证。

这个选择成立的条件是一次主服务请求失败足以让当前模型对象的后续调用继续使用备用服务，恢复主服务交给下次创建模型对象。如果 any-llm 提供可观察的跨 provider 路由，或者常驻进程需要在不重启的情况下探测并恢复主服务，就重新评估并用带健康状态和冷却时间的路由替换当前粘性开关。

## 模型对象的关闭使用兼容探测

any-llm 当前没有统一的关闭接口。应用先尝试 provider 的 `aclose()` 或 `close()`，再清理它直接持有的已知 SDK 资源。

这个做法对对象布局有有限依赖，但能避免应用创建的网络资源泄漏。关闭失败只记录安全的类型信息，不能覆盖已经发生的业务异常。

any-llm 提供稳定的统一生命周期接口后，应删除属性探测并直接使用该接口。

## 未知预警解除 ID 不阻断简报

模型可能根据历史内容返回已经过期或不存在的预警 ID。这些 ID 不会删除任何状态，也不会出现在用户正文中。

应用在保存前过滤未知 ID，只记录不同 ID 的数量，避免为没有副作用的记账错误消耗一次模型修复并丢弃整份简报。

如果解除字段开始影响正文或触发外部操作，就恢复严格失败，并先把预警身份交给确定性的服务或应用逻辑管理。

## 历史预算目前只限制天气快照

天气 API 快照每次调度都会产生，是历史输入中稳定增长的部分。RSS 文章和已发布简报目前频率较低，仍只受时间窗口限制。

因此文档数和字符数预算目前只应用于历史天气快照。应用记录完整模型输入的字符数，但不记录正文。

如果 RSS 数量、地点数或简报频率明显增加，或者持续出现输入过长和模型超时，就改成覆盖所有历史类别的统一预算。

## 快照额外保存可比较值

面向用户的天气文本包含更新时间等易变内容，不能直接判断天气是否真的变化。各适配器因此提供 `history_value`，只排除不会改变结论的元数据。

这会在 SQLite 中多保存一份确定性表示，但避免通过解析渲染文本来猜测语义，也让预算告警可以稳定去重。

如果适配器难以维护稳定值、经常漏掉重要字段，或重复存储成为容量问题，就改用带版本的结构化值或摘要指纹，并设计迁移规则。

## 不用模型压缩单份超长历史快照

在主调用前增加一次模型摘要会增加费用、超时和故障面，也无法保证预警、空气质量和过敏原信息不丢失。

内置适配器改为从已校验的领域对象生成较短的确定性摘要。当前轮仍使用完整上下文，摘要只用于历史比较。

最新值和窗口基线即使摘要后仍无法容纳时，应用继续生成简报并发送运维告警。如果确定性摘要长期无法满足实际质量，再评估可缓存、可观察且与主调用隔离的压缩方案。

## 主简报确认后再保存结果

主简报和完整转发正文不是同一个平台操作。主简报被平台接受后，应用立即保存本轮结果，并把待发正文登记到同一事务中。正文随后逐篇投递和确认。

这样正文中途失败不会让下一轮重新生成主简报，也不会重发已经确认的前项。但平台接受消息后、本地确认前崩溃，仍可能造成重复。

当前接受少量重复，因为 Telegram 没有可复用的幂等键，静默丢失比重复更糟。

如果平台提供稳定消息身份、重复开始造成实际问题，或需要多个 worker 并发投递，就把幂等键、租约和确认协议放到投递适配器中。

## 原生 Windows 不在支持范围内

项目支持 Linux 容器和 POSIX 环境中的直接运行，不支持原生 Windows。daemon 所有权和完整业务运行使用 `fcntl` 锁协调共享 state 目录的进程。

当前部署文档以 Docker 为推荐方式，CI 也只覆盖 Linux 和 macOS，因此不为未支持的平台增加另一套锁实现或第三方依赖。

如果以后把原生 Windows 纳入支持范围，就应引入经过维护的跨平台文件锁方案、声明新的平台契约，并增加 Windows CI，而不是在调用处零散增加条件分支。

## 异步流程仍使用同步 SQLite 和定位缓存操作

状态库和定位缓存直接在事件循环线程中执行短小的本地操作，没有引入异步 SQLite 依赖。地点配置回写包含同步文件刷新，因此 CLI 使用 `asyncio.to_thread` 执行这部分操作。

当前任务按小时运行、地点按顺序处理，状态量受保留窗口限制。正常的本地磁盘操作远短于天气、RSS、定位和模型网络请求。

这项选择要求状态文件位于低延迟本地磁盘或同等持久卷，并且没有持续的事件循环停顿、锁等待或调度漂移。

如果地点开始并行处理、状态迁移到网络存储、写入量明显增加，或监控发现阻塞，就测量延迟并重新设计持久化边界。

不能简单把现有连接包进 `asyncio.to_thread`，因为 SQLite 连接具有线程亲和性。

## 第三方 DEBUG 日志保持关闭

模型和 HTTP SDK 的 DEBUG 内容不受应用控制，可能包含凭据、请求地址、正文或位置上下文。因此 `DEBUG=true` 只提高应用 logger 的级别，第三方 logger 仍保持 WARNING。

完整正文诊断只记录应用自己控制的字段，并要求额外的限时开关。

如果第三方 SDK 以后提供稳定的结构化安全日志接口，可以评估接入；不能依赖异常消息或事后正则清洗来保护隐私。

## Bark 暂不迁移到 Apprise

Telegram 投递已迁移到 Apprise，由维护中的通知库承担目标配置、原始纯文本分块和静默选项。Telegram 与 stdout 共用带完整来源 URL 的纯文本 renderer。项目只保留配置组合、平台长度策略，以及一个以纯文本模式逐分片发送请求并检查 Telegram JSON `ok=true` 的 SDK 兼容 sender；Apprise 1.12 只检查 HTTP 状态，不能作为严格成功确认。同步 Apprise 通知整体放入单个 worker，避免阻塞事件循环，同时防止同一长消息的分片并发到达。Apprise 自身日志保持关闭，避免第三方错误正文、目标或消息进入运行日志。

Apprise 1.12 不提供安全的结构化 Telegram 目标可用性类别，兼容 sender 也不解析错误正文来推断目标是否永久不可用。因此 briefing 投递失败后，复用同一 Telegram 目标的运维告警仍会有界尝试一次；瞬时失败可能在第二次请求时恢复，永久失败则只增加一次失败请求和一条带安全阶段、HTTP 状态或异常类型的日志，不会递归发送告警。相比恢复 Telegram 错误正文映射，这一取舍保留了更小且不依赖私密第三方文本的边界。Apprise 提供不暴露响应正文的结构化目标可用性类别后，再恢复提前跳过永久不可用目标。

Apprise 1.12.0 的 Bark 插件不支持项目使用的 AES-GCM `ciphertext` 和逐条随机 IV，也只按 HTTP 状态判断成功。Bark 因此继续作为与 Apprise 同级的自维护 publisher，以保留认证加密、严格 JSON 成功确认和安全错误分类。

当 Apprise 的 Bark 插件同时支持现有加密协议和严格成功确认时，再重新评估迁移。迁移不能降低加密、响应验证、消息长度或隐私日志边界。

## 服务状态使用事件 feed，不轮询完整历史 API

截至 2026-07-24，DeepSeek、OpenAI、Anthropic 和 Kimi 的官方状态页都提供无需认证的事件 feed。需求只允许转发官方故障、进展和恢复消息，并要求忽略不值得提醒的页面变化；feed 恰好提供稳定事件身份、最新官方正文和恢复修订，下载量也小于重复读取完整事件历史 API。

feed 不保证每条消息都提供完整组件清单。项目只在官方标题或受影响组件名称明确时区分网页、API 和其他服务，不用当前组件快照补写官方消息没有声明的影响范围。

如果厂商提供带修订游标、条件请求、推送和受影响组件的正式只读接口，应重新评估传输方式。provider 领域契约不依赖 RSS，可以替换适配器而不改变监控和通知编排。

服务状态不进入天气简报的内容生成流程。通知价值判断已从天气内容模型中分离为共用策略；服务消息另行判断是否值得打扰。消息不是英语或用户指定语言时才允许调用大语言模型忠实翻译；翻译不是事实来源，失败时保留官方原文。如果服务状态出现不依赖语义判断的稳定机器字段，或者官方提供可直接选择用户语言的消息，应重新评估相应的大语言模型调用。

## 暂不接入智谱服务状态

截至 2026-07-24，没有找到能确认归属且可稳定机器读取的智谱官方状态页：候选域名未形成有效的公开状态服务，官方文档也没有给出状态入口。用第三方探针会把外部推测冒充厂商声明，因此本轮不注册 `zhipu` provider。

当智谱官方文档链接到公开状态页、只读 API 或事件订阅时再接入；届时仍需分别建模网页服务和 API 服务。
